# Deployment

Nothing here has been deployed yet: it needs your accounts, and some steps create paid resources.
Every step below is something you run or approve.

```text
game.example.com  ── Vercel ──  static client (apps/web/dist)
api.example.com   ── Render ──  Docker: game server + API (WSS)  ── Render PostgreSQL
```

The client and the server live on different origins. The client learns the server address at
build time (`VITE_SERVER_URL`); the server only answers CORS for `ALLOWED_ORIGINS`.

## 1. Game server on Render (first option)

Prerequisites: the repository on GitHub/GitLab, a Render workspace.

1. In Render, **New → Blueprint**, select the repository. `render.yaml` defines:
   - `scrapline-server`: Docker web service from `docker/server.Dockerfile`, region `frankfurt`,
     health check `/health`, one instance, `maxShutdownDelaySeconds: 300`.
   - `scrapline-db`: PostgreSQL 17, private network only (`ipAllowList: []`).
2. When prompted, set `ALLOWED_ORIGINS` to your client origins, comma separated, for example
   `https://game.example.com,https://scrapline.vercel.app`.
   `TOKEN_SECRET` is generated by Render; `DATABASE_URL` is wired from the database.
3. Review the plans before applying (see *Costs*). Apply.
4. Migrations run at boot. Check `https://<service>.onrender.com/health` →
   `{"status":"ok","db":"postgres"}`.

WebSockets work on Render web services without extra configuration. TLS is terminated by Render,
so the client uses `https://` and `wss://` automatically.

**Deploys and running matches.** During a deploy Render moves new traffic to the new instance and
sends SIGTERM to the old one about 60 s later; open WebSockets on the old instance end when it
exits. The server handles SIGTERM by locking its rooms, telling players the room will close after
the current match, and waiting up to `SHUTDOWN_DRAIN_SEC` (270 s in the Blueprint, below the 300 s
shutdown delay) for matches to end. Players in a match when the old instance finally exits see
"The server restarted for an update" and can join a new match. Deploy at quiet hours.

**Sizing.** Measured: an 8-player room costs ~0.3 ms per 50 ms tick (max ~4.4 ms) on one core.
`0.5c-512mb` should host several rooms; move to `1c-2g` if `/health` latency or tick intervals
degrade. Keep **one instance** until Redis presence is added (see ARCHITECTURE.md, Scaling).

## 2. Alternative: Scaleway

Recommended: a **Scaleway Instance** running the same Docker image, with Caddy (or any reverse
proxy) for TLS:

```bash
docker build -f docker/server.Dockerfile -t scrapline-server .
docker run -d --restart=always -p 127.0.0.1:2567:2567 --env-file server.env scrapline-server
# Caddyfile
api.example.com {
  reverse_proxy 127.0.0.1:2567
}
```

Database: Scaleway Managed PostgreSQL (set `DATABASE_URL`, and `DATABASE_SSL=true` if the
connection requires TLS) or PostgreSQL on the same instance for small deployments.

Scaleway Serverless Containers: Scaleway's changelog states that containers configured with
custom domains are compatible with WebSockets (2025-08-28). Their connection and request time
limits and scale-to-zero behaviour must be checked before running long-lived game rooms there;
a room must live in exactly one container, so set min = max = 1 instance.

## 3. Client on Vercel

1. **New Project**, import the repository, set **Root Directory** to `apps/web`.
   `apps/web/vercel.json` sets install/build commands for the pnpm monorepo, output `dist`,
   SPA rewrites (`/?join=CODE` invite links), immutable caching for hashed assets, and security
   headers (CSP allows `connect-src https: wss:` so the API host can live elsewhere).
2. Environment variable (Production and Preview): `VITE_SERVER_URL=https://api.example.com`.
3. Deploy. Add the resulting `*.vercel.app` URL (and your domain) to the server's `ALLOWED_ORIGINS`.

## 4. Domains and DNS

Example with `example.com` (do not change real DNS records without checking existing ones):

| Host | Type | Value | Where |
|---|---|---|---|
| `game.example.com` | CNAME | `cname.vercel-dns.com` (Vercel shows the exact target) | Vercel → Project → Domains |
| `api.example.com` | CNAME | `<service>.onrender.com` | Render → Service → Settings → Custom Domains |

Both platforms issue TLS certificates automatically once the records resolve. Then:

- Vercel: `VITE_SERVER_URL=https://api.example.com`, redeploy.
- Render: `ALLOWED_ORIGINS=https://game.example.com,...`, redeploy.

If the domain is managed by Vercel DNS, add the `api` CNAME there.

## 5. Environment variables

Server (`apps/server/.env.example`):

| Variable | Required in prod | Purpose |
|---|---|---|
| `NODE_ENV` | yes (`production`) | Enables strict checks |
| `PORT`, `HOST` | no | Default `2567`, `0.0.0.0` |
| `DATABASE_URL` | yes | PostgreSQL connection string |
| `DATABASE_SSL` | no | `true` when the provider requires TLS |
| `TOKEN_SECRET` | yes (32+ chars) | Signs guest identity tokens. Rotating it logs every guest out |
| `ALLOWED_ORIGINS` | yes | Client origins allowed by CORS |
| `SHUTDOWN_DRAIN_SEC` | no | Match draining on SIGTERM |
| `LOG_LEVEL` | no | `info` by default |
| `ENABLE_DEBUG_ROUTES` | must be `false` | Debug endpoints and test spawns; refused in production |

Client: `VITE_SERVER_URL` (build time).

## 6. Post-deploy checklist

- [ ] `GET https://api.example.com/health` → 200, `db: postgres`
- [ ] Open the game on two different networks (e.g. desktop + phone hotspot laptop), create a
      private room on one, join with the link on the other, play a match to the end
- [ ] Results screen shows XP, Profile shows updated stats after a reload
- [ ] Browser devtools: WebSocket connects with `wss://`, no CORS errors
- [ ] `GET https://api.example.com/api/rooms` from another origin has no
      `Access-Control-Allow-Origin` header
- [ ] Redeploy the server during a match: players get the restart notice

## Costs

No prices are stated here on purpose: plans and prices change, and the Blueprint values are only
starting points. Check before applying:

- Render pricing for web services (`0.5c-512mb`) and PostgreSQL (`0.1c-256mb`), plus bandwidth.
  A Render workspace subscription does not by itself include unlimited compute.
- Vercel: the client is a static site (no serverless functions), so usage is mostly bandwidth.
- Scaleway: Instance type, Managed Database tier, egress.

Bandwidth estimate per player: ~3.6 KB/s down and ~1.5 KB/s up while playing (≈ 13 MB down per
hour), plus the one-time client download (~0.6 MB gzipped).
