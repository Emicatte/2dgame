# Host mode (no game server)

The player who creates an arena hosts it: the authoritative room runs in that player's browser
tab, and the other players' browsers connect to it directly over WebRTC. Only a small signaling
endpoint is needed to exchange connection details when someone joins. It runs as a Vercel Function
backed by a free Upstash Redis store, so the whole game deploys on Vercel alone.

```text
             (1) create / join / poll / answer, only while connecting
 Host tab ──HTTPS──► Vercel: /api/p2p ◄──HTTPS── Guest tab
 (room +  ◄═══════ WebRTC DataChannel (game traffic) ═══════► (client)
  client)                    │
                       Upstash Redis (room codes, offers/answers, expire in 1–2 min)
```

## What runs where

| Piece | Code | Notes |
|---|---|---|
| Authoritative room in the host's tab | `apps/web/src/p2p/HostRoom.ts` | Ports the private-room logic of `ArenaRoom` (lobby, settings, ready/start, countdown, match, results, practice targets, AFK removal) onto the **same** `GameSimulation`, state mirroring and scoring as the dedicated server, at 20 Hz. State goes out with the same `@colyseus/schema` encoder and per-player views as Colyseus (owner-only fields reach only their owner). |
| Guest room | `apps/web/src/p2p/PeerRoom.ts` | Implements the Colyseus SDK Room API subset the client uses, decodes state like the SDK, measures ping, sends keepalives, and reconnects within 20 s with its seat token. |
| Host's own player | `HostRoom` itself | The host's client reads the authoritative state directly (zero latency). |
| Transport | `apps/web/src/p2p/link.ts`, `rtc.ts` | One reliable, ordered DataChannel per guest; offers/answers without trickle ICE (each side gathers candidates first, max 3.5 s). |
| Signaling | `apps/web/src/p2p/signalServer.ts` → `apps/web/api/p2p.js` | Vercel Function, committed as plain JavaScript generated by `pnpm --filter @scrapline/web build:api` (precaution: the project's TypeScript 7 has no JavaScript compiler API for a TypeScript function build to use); a test fails if it is stale. The Vite dev/preview server mounts the same handler with an in-memory store. |
| Profile | `apps/web/src/state/localProfile.ts` | Callsign, XP, level, stats and loadout in `localStorage` on each computer. No global leaderboard. |

The game scene, HUD, lobby and results screens are unchanged: they talk to a "room" object that is
a Colyseus room in server mode, a `HostRoom` for the host, or a `PeerRoom` for guests.

**Which mode a build uses** (`apps/web/src/net/api.ts`): `VITE_NET_MODE=p2p|server` if set;
otherwise a build with `VITE_SERVER_URL` uses the server; a production build without it (the
current Vercel deployment) uses host mode; `pnpm dev` uses the local server.

## Set up on Vercel

1. Vercel → project → **Storage** → **Create Database** → **Upstash for Redis**, plan **Free**,
   region near the players (e.g. Frankfurt). **Connect Project** to the game's project for all
   environments, default prefix. Vercel adds `KV_REST_API_URL` / `KV_REST_API_TOKEN`
   (`UPSTASH_REDIS_REST_*`, a custom prefix, or an Upstash `REDIS_URL` are also recognised).
2. Redeploy (Deployments → ⋯ → Redeploy) so the function sees the variables.
3. Check `https://<your-app>.vercel.app/api/p2p` → `{"service":"scrapline-signaling","storage":"connected"}`.
   `missing` = the store is not connected to this project/environment; `unreachable` = wrong
   credentials or Upstash is down.

Budget: Upstash's free plan allows 500,000 commands per month. A hosted arena polls for join
requests every 1.5 s in the lobby and every 4 s during a match (3 commands per poll), roughly
4,000 commands per hour of hosting; a join costs about 20.

## School and office networks

Direct connections need the two computers to reach each other. That works on most home networks
and on many school networks, but some block it (Wi-Fi client isolation, strict firewalls, no
UDP). Symptom: joining fails with "Could not connect to the host's computer" after ~15 s, while
the code is accepted.

Fix: a TURN relay, which forwards the traffic when a direct path is impossible (also over TCP/TLS
port 443). The signaling function hands relays to the browsers when configured:

- Cloudflare Realtime TURN: create a TURN key in the Cloudflare dashboard, then set
  `CLOUDFLARE_TURN_KEY_ID` and `CLOUDFLARE_TURN_API_TOKEN` on the Vercel project (short-lived
  credentials are generated per session). Cloudflare lists a free tier of 1,000 GB, then
  $0.05/GB; one player uses roughly 20 MB per hour. Check their current terms before enabling.
- Any other TURN server: `TURN_URLS` (comma separated, e.g. `turns:turn.example.com:443`),
  `TURN_USERNAME`, `TURN_CREDENTIAL`.

The lobby does not show which path a guest uses; `PeerRoom.path` holds it ("direct (…)" or
"relayed (TURN)") for debugging.

## Rules and limits

- The host's tab must stay open. Keep it in front while playing: the room ticks from a worker
  timer so a background tab keeps running, but the host's own game is not rendered then.
- When the host leaves or closes the tab, the arena ends for everyone ("The host closed the
  arena."). There is no host migration.
- Guests that lose the connection keep their seat for 20 s and rejoin automatically; a page reload
  rejoins the same seat (seat token in `sessionStorage`).
- Host and guests must run the same build: after a deploy, everybody reloads (a guest on another
  build is refused with a clear message).
- Trust: the host's browser is the referee. A host can cheat in their own arena, and each player's
  XP is recorded by their own browser. That is acceptable among friends; competitive play and the
  global leaderboard need the dedicated server (still in the code, see DEPLOYMENT.md).
- Guests are validated like on the dedicated server: every message is schema-checked, unknown or
  malformed messages and floods (>150 msg/s) remove the sender, one seat per profile, host-only
  actions are checked by the host.
- Signaling: room codes are 5 characters from the dedicated server's alphabet; only the holder of
  the host key (stored hashed) can read offers, answer or close; offers/answers expire in 60 s, a
  room registration in 120 s without a host poll; creation and joins are rate limited per address
  (generous, because a class shares one public address).

## Tests

- `apps/web/test/signal.test.ts`: signaling protocol, authorization, expiry, rate limits, HTTP
  wrapper, Upstash REST commands, environment discovery, ICE/TURN configuration.
- `apps/web/test/hostmode.test.ts`: host and guests over in-memory links: join, owner-only
  fields, full match flow (ready/start/countdown/inputs/events/results), seat kept on drop and
  reconnect, page-reload resume, duplicate profile / other build / full room refused, malformed
  messages, kick, host closing, ping.
- `tests/e2e-p2p/hostmode.spec.ts`: two separate Chrome processes, real WebRTC: create arena,
  join by code, both players move and see each other, guest reloads mid-match and takes its seat
  back, host closes the tab and the guest is told. `pnpm test:e2e:p2p` (dev server) and
  `E2E_P2P_PREVIEW=1 pnpm test:e2e:p2p` (production build, default mode).

Not testable here: real school networks (NAT, client isolation, firewalls) and TURN relays.
